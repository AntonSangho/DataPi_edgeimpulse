# Phase 0 — BH1750 센서 특성 측정

> 상태: **1차 측정 완료** (2026-08-05, 실내 형광등 배경 ~128 lx)
> 남은 것: 제스처별 동적 범위 측정 (보드 앞에서 직접 손동작 필요)

## 왜 이걸 먼저 하는가

*AI at the Edge* Ch.6 "Determining Feasibility → Technological Feasibility"의 요지는
**모델을 만들기 전에 센서가 그 현상을 담을 대역폭과 민감도를 가졌는지부터 확인하라**는 것이다.
조도 센서로 손동작을 구분하려면 두 가지가 성립해야 한다.

1. **시간 해상도** — 제스처(0.3~1초)를 여러 샘플로 쪼갤 만큼 빨라야 한다.
2. **진폭 분리도** — 손동작에 의한 lux 변동이 `idle`의 잡음보다 뚜렷하게 커야 한다.

결과적으로 이 단계에서 **계획의 가정 하나가 틀렸고 드라이버 버그 두 개가 나왔다.**
데이터를 수백 개 모은 뒤였다면 전부 다시 모아야 했을 것이다.

## 1. 변환 시간과 잡음 (실측)

배경 조도를 고정한 상태에서, 레지스터를 0으로 지우고 측정을 재시작한 뒤
새 값이 채워질 때까지의 시간을 쟀다. (`src/characterize.py`의 `measure_conversion_time`)

| 설정 | 변환 ms | 최대 Hz | 이론 ms | raw 범위 | 지터 (cnt) |
|---|---:|---:|---:|---|---:|
| **HIGH mt=31** | **52.6** | **19.0** | 53.9 | 70~71 | **0.02** |
| HIGH mt=45 | 76.8 | 13.0 | 78.3 | 101~101 | 0.00 |
| HIGH mt=69 | 116.9 | 8.6 | 120.0 | 156~156 | 0.00 |
| HIGH2 mt=31 | 52.6 | 19.0 | 53.9 | 311~312 | 0.01 |
| LOW mt=31 | 1.1 | (944) | 7.2 | 0~128 | 10.91 |
| LOW mt=69 | 2.2 | (456) | 16.0 | 96~224 | 13.71 |

### 계획의 가정이 틀렸다 — 저해상도 모드는 쓸 수 없다

계획에서는 "L-Resolution + MTreg=31이면 139 Hz가 나온다"고 봤다. 실측은 정반대다.

- **변환 시간이 이론값보다 훨씬 짧게 나온다** (1.1 ms vs 이론 7.2 ms).
  즉 저해상도 모드는 변환이 끝나기 전의 **미완결 값을 돌려주고 있다.**
- 조도가 완전히 고정된 상태에서 raw가 `0~128`을 오간다.
  지터 10.9 카운트 — 고해상도의 **500배**다.

이 잡음은 손동작 신호를 그대로 덮어버린다. **저해상도 모드는 배제한다.**

### 확정: HIGH resolution, MTreg = 31

깨끗한 값을 주는 설정 중 가장 빠른 것이 `HIGH mt=31`이고, 이론값(53.9 ms)과
실측(52.6 ms)이 일치한다. **최대 19.0 Hz.**

MTreg는 데이터시트 최솟값이 31이므로 이보다 빠르게 만들 수는 없다.
HIGH2는 같은 속도에 분해능만 0.5 lx로 좋아지지만, 배경 잡음이 이미 0에 가까워 실익이 없다.

## 2. 샘플레이트 재조정 — 25 Hz → 16.6 Hz

계획은 25 Hz / 창 2000 ms(50 샘플)를 목표로 했다. 센서 상한이 19 Hz이므로 지킬 수 없다.
계획 문서의 조정 규칙("실측치로 낮춘다")을 적용한다.

| 항목 | 계획 | **확정** |
|---|---|---|
| 해상도 / MTreg | LOW / 31 | **HIGH / 31** |
| 샘플 주기 | 40 ms | **60 ms** |
| 샘플레이트 | 25 Hz | **16.6 Hz** |
| 창 길이 | 2000 ms | **2000 ms** |
| 창당 샘플 수 | 50 | **33** |
| stride | 500 ms | 500 ms |

**60 ms 주기를 고른 이유**: 변환이 52.6 ms이므로 53 ms 주기로 읽으면 경계에서 같은 값을
두 번 읽는 일이 생긴다. 60 ms는 약 14%의 여유를 두면서 16.6 Hz를 확보한다.

**창 길이를 2000 ms로 유지한 이유**: 50 샘플을 채우려면 3000 ms가 필요한데,
제스처 인식에서 3초 지연은 체감상 너무 느리다. 33 샘플이면 Nyquist 주파수가 8.3 Hz라
손 흔들기(대략 1~5 Hz)를 담기에 충분하다. 샘플 수보다 반응성을 택했다.

## 3. 드라이버 버그 2건

원본 [`flrrth/pico-bh1750`](https://github.com/flrrth/pico-bh1750)에서 발견해
`src/lib/bh1750.py`에서 수정했다.

### (1) 해상도 판별 오류

```python
# 원본 (bh1750.py:72, :115)
sleep_ms(24 if self._measurement_time == BH1750.RESOLUTION_LOW else 180)
```

`_measurement_time`은 31~254인데 `RESOLUTION_LOW`는 2다. 항상 거짓이 되어
저해상도 모드에서도 180 ms를 대기한다. → `self._resolution`과 비교하도록 수정.

(다만 위 1절에서 저해상도 자체를 배제했으므로, 이 수정은 실사용에는 영향이 없다.)

### (2) MTreg lux 환산 방향이 반대 — 이쪽이 중요하다

```python
# 원본 (bh1750.py:94)
lux = raw / (1.2 * (69 / self._measurement_time))
```

MTreg를 줄이면 감도가 낮아져 **같은 밝기에서 raw 카운트가 작아진다.**
따라서 나눠야 할 값은 `(mt / 69)`이지 `(69 / mt)`가 아니다.

`mt = 69`(기본값)에서는 두 식이 일치하기 때문에, 기본 설정으로만 쓰면 절대 드러나지 않는다.
우리는 속도를 위해 `mt = 31`을 쓰므로 정면으로 걸린다.

**수정 전후 (배경 조도 고정, 같은 조명):**

| MTreg | 원본 식 | 수정 후 |
|---|---:|---:|
| 31 | 26.3 lx | **128.0 lx** |
| 45 | 54.9 lx | **127.8 lx** |
| 69 | 130.0 lx | **127.5 lx** |
| 120 | — | **127.9 lx** |

수정 후 MTreg를 바꿔도 값이 일치한다. 이것이 정답이라는 증거다.

원본 식을 그대로 뒀다면 lux 절댓값이 5배 틀린 채로 학습됐을 것이다.
분류만 한다면 스케일이 일정해서 티가 안 났겠지만, Phase 3에서 C 드라이버를 직접 쓰는 순간
학습 때와 추론 때의 스케일이 어긋나 모델이 통째로 망가진다.
