# Phase 0 — BH1750 센서 특성 측정

> 상태: **완료** (2026-08-05, 실내 형광등 배경 ~130 lx)

## 왜 이걸 먼저 하는가

*AI at the Edge* Ch.6 "Determining Feasibility → Technological Feasibility"의 요지는
**모델을 만들기 전에 센서가 그 현상을 담을 대역폭과 민감도를 가졌는지부터 확인하라**는 것이다.
조도 센서로 손동작을 구분하려면 두 가지가 성립해야 한다.

1. **시간 해상도** — 제스처(0.3~1초)를 여러 샘플로 쪼갤 만큼 빨라야 한다.
2. **진폭 분리도** — 손동작에 의한 lux 변동이 `idle`의 잡음보다 뚜렷하게 커야 한다.

결과적으로 이 단계에서 **계획의 가정 하나가 틀렸고, 드라이버 버그 두 개가 나왔고,
측정 방법 자체의 결함 두 개가 나왔다.** 데이터를 수백 개 모은 뒤였다면 전부 다시 모아야 했을 것이다.

최종 결론은 **가능하다**이지만, 그 결론에 도달하기까지 세 번을 측정했고
그중 두 번은 "불가능"이라고 잘못 답했다. 어떻게 틀렸는지가 4절에 기록돼 있다.

## 1. 변환 시간과 잡음 (실측)

배경 조도를 고정한 상태에서, 레지스터를 0으로 지우고 측정을 재시작한 뒤
새 값이 채워질 때까지의 시간을 쟀다. (`src/characterize.py`의 `measure_conversion_time`)

| 설정 | 변환 ms | 최대 Hz | 이론 ms | raw 범위 | 지터 (cnt) |
|---|---:|---:|---:|---|---:|
| **HIGH mt=31** | **52.6** | **19.0** | 53.9 | 70~71 | **0.02** |
| HIGH mt=45 | 76.8 | 13.0 | 78.3 | 101~101 | 0.00 |
| HIGH mt=69 | 116.9 | 8.6 | 120.0 | 156~156 | 0.00 |
| HIGH2 mt=31 | 52.6 | 19.0 | 53.9 | 311~312 | 0.01 |
| LOW mt=31 | 1.1 | (944) | 7.2 | 0~128 | 10.91 |
| LOW mt=69 | 2.2 | (456) | 16.0 | 96~224 | 13.71 |

### 계획의 가정이 틀렸다 — 저해상도 모드는 쓸 수 없다

계획에서는 "L-Resolution + MTreg=31이면 139 Hz가 나온다"고 봤다. 실측은 정반대다.

- **변환 시간이 이론값보다 훨씬 짧게 나온다** (1.1 ms vs 이론 7.2 ms).
  즉 저해상도 모드는 변환이 끝나기 전의 **미완결 값을 돌려주고 있다.**
- 조도가 완전히 고정된 상태에서 raw가 `0~128`을 오간다.
  지터 10.9 카운트 — 고해상도의 **500배**다.

이 잡음은 손동작 신호를 그대로 덮어버린다. **저해상도 모드는 배제한다.**

### 확정: HIGH resolution, MTreg = 31

깨끗한 값을 주는 설정 중 가장 빠른 것이 `HIGH mt=31`이고, 이론값(53.9 ms)과
실측(52.6 ms)이 일치한다. **최대 19.0 Hz.**

MTreg는 데이터시트 최솟값이 31이므로 이보다 빠르게 만들 수는 없다.
HIGH2는 같은 속도에 분해능만 0.5 lx로 좋아지지만, 배경 잡음이 이미 0에 가까워 실익이 없다.

**재현성**: 서로 다른 시점에 3회 측정했고 변환 시간은 모든 설정에서 ±0.1 ms 이내로 일치했다
(HIGH mt=31 → 52.6 / 52.6 / 52.6 ms). 저해상도의 지터만 10.1~19.2 카운트로 크게 흔들렸는데,
값 자체가 무작위이므로 당연한 결과다.

## 2. 샘플레이트 재조정 — 25 Hz → 16 Hz

계획은 25 Hz / 창 2000 ms(50 샘플)를 목표로 했다. 센서 상한이 19 Hz이므로 지킬 수 없다.
계획 문서의 조정 규칙("실측치로 낮춘다")을 적용한다.

| 항목 | 계획 | **확정** |
|---|---|---|
| 해상도 / MTreg | LOW / 31 | **HIGH / 31** |
| 샘플 주기 | 40 ms | **62.5 ms** |
| 샘플레이트 | 25 Hz | **16 Hz** |
| 창 길이 | 2000 ms | **2000 ms** |
| 창당 샘플 수 | 50 | **32** |
| stride | 500 ms | 500 ms |

**62.5 ms 주기를 고른 이유**: 변환이 52.6 ms이므로 53 ms 주기로 읽으면 경계에서 같은 값을
두 번 읽는 일이 생긴다. 처음에는 60 ms(16.6 Hz)로 잡았으나 Phase 1에서 고쳤다 —
`edge-impulse-data-forwarder --frequency 16`으로 붙으면 Studio는 샘플 간격을 62.5 ms로
기록하므로, 장치가 60 ms로 보내면 데이터셋 라벨과 실제가 **4% 어긋난다.**
`wave`/`swipe`는 주파수로만 구분되므로 이 오차가 그대로 스펙트럼을 민다.
장치를 데이터셋에 맞췄고, 변환 시간 대비 여유는 오히려 19%로 늘었다.

**창 길이를 2000 ms로 유지한 이유**: 50 샘플을 채우려면 3000 ms가 필요한데,
제스처 인식에서 3초 지연은 체감상 너무 느리다. 32 샘플이면 Nyquist 주파수가 8 Hz라
손 흔들기(대략 1~5 Hz)를 담기에 충분하다. 샘플 수보다 반응성을 택했다.

## 3. 드라이버 버그 2건

원본 [`flrrth/pico-bh1750`](https://github.com/flrrth/pico-bh1750)에서 발견해
`src/lib/bh1750.py`에서 수정했다.

### (1) 해상도 판별 오류

```python
# 원본 (bh1750.py:72, :115)
sleep_ms(24 if self._measurement_time == BH1750.RESOLUTION_LOW else 180)
```

`_measurement_time`은 31~254인데 `RESOLUTION_LOW`는 2다. 항상 거짓이 되어
저해상도 모드에서도 180 ms를 대기한다. → `self._resolution`과 비교하도록 수정.

(다만 위 1절에서 저해상도 자체를 배제했으므로, 이 수정은 실사용에는 영향이 없다.)

### (2) MTreg lux 환산 방향이 반대 — 이쪽이 중요하다

```python
# 원본 (bh1750.py:94)
lux = raw / (1.2 * (69 / self._measurement_time))
```

MTreg를 줄이면 감도가 낮아져 **같은 밝기에서 raw 카운트가 작아진다.**
따라서 나눠야 할 값은 `(mt / 69)`이지 `(69 / mt)`가 아니다.

`mt = 69`(기본값)에서는 두 식이 일치하기 때문에, 기본 설정으로만 쓰면 절대 드러나지 않는다.
우리는 속도를 위해 `mt = 31`을 쓰므로 정면으로 걸린다.

**수정 전후 (배경 조도 고정, 같은 조명):**

| MTreg | 원본 식 | 수정 후 |
|---|---:|---:|
| 31 | 26.3 lx | **128.0 lx** |
| 45 | 54.9 lx | **127.8 lx** |
| 69 | 130.0 lx | **127.5 lx** |
| 120 | — | **127.9 lx** |

수정 후 MTreg를 바꿔도 값이 일치한다. 이것이 정답이라는 증거다.

원본 식을 그대로 뒀다면 lux 절댓값이 5배 틀린 채로 학습됐을 것이다.
분류만 한다면 스케일이 일정해서 티가 안 났겠지만, Phase 3에서 C 드라이버를 직접 쓰는 순간
학습 때와 추론 때의 스케일이 어긋나 모델이 통째로 망가진다.

## 4. 제스처별 동적 범위 (실측)

`src/gesture_range.py`, 실내 형광등, 배경 129.8 lx, HIGH mt=31 / 16.7 Hz / 5초씩.
(이 측정은 주기를 62.5 ms로 고치기 전에 했다. 진폭 통계는 주기와 무관하므로 그대로 유효하다.)

| 클래스 | min | max | mean | 범위 | 최대 샘플간 변화 |
|---|---:|---:|---:|---:|---:|
| idle | 128.0 | 131.7 | 129.8 | 3.7 | 1.9 |
| cover | 5.6 | 7.4 | 5.7 | 1.9 | 1.9 |
| wave | 42.7 | 129.8 | 107.8 | 87.2 | 57.5 |
| swipe | 46.4 | 131.7 | 124.6 | 85.3 | 53.8 |

### 판정: 3개 클래스 모두 분리 가능

| 클래스 | 판정 | 근거 |
|---|---|---|
| cover | 구분 가능 | 배경 대비 **레벨차 96%** (129.8 → 5.7 lx) |
| wave | 구분 가능 | 최대 변화가 idle의 **31.0배** |
| swipe | 구분 가능 | 최대 변화가 idle의 **29.0배** |

`idle`과 `cover`의 최대 샘플간 변화가 둘 다 1.9 lux로 같은데, 이것은
**mt=31에서의 1 LSB**다 (`1 / (1.2 × 31/69) = 1.855 lux`). 즉 두 클래스 모두
잡음 바닥에 붙어 있는 완전히 정적인 신호이고, 서로는 레벨로 23배 떨어져 있다.

### 판정 기준을 고쳤다 — 1차 측정의 교훈

1차 측정에서는 세 클래스가 전부 "구분 어려움"으로 나왔다. 원인이 둘이었고
**둘 다 센서가 아니라 측정 방법의 문제**였다.

**(1) 판정 지표가 클래스에 맞지 않았다.** 모든 클래스를 "샘플간 변화량"으로 판정했는데,
`cover`는 덮고 **가만히 있는** 동작이라 변화량이 작은 것이 정상이다.
실제로는 배경 대비 23배 어두워지는 가장 쉬운 클래스인데 기준이 이를 놓쳤다.
→ `cover`는 **레벨**, `wave`/`swipe`는 **변화량**으로 판정하도록 분리했고,
주 지표에서 떨어져도 다른 지표로 분리되면 살려주도록 했다.

**(2) `idle` 기준값이 오염됐다.** 1차 `idle`은 `min=3.7 / max=131.7`이었다.
3.7 lx는 센서가 거의 완전히 가려진 값 — 측정 중 손이나 그림자가 지나갔다.
`idle`은 **모든 판정의 분모**라서, 이게 오염되면 나머지가 전부 무너진다.
→ 변동폭이 평균의 25%를 넘으면 오염으로 보고 최대 3회 자동 재측정하도록 했다.
2차 측정의 `idle` 변동폭은 평균의 2.8%다.

## 4-1. Phase 2로 넘기는 위험: `wave`와 `swipe`가 요약통계로는 구분되지 않는다

| | wave | swipe | 차이 |
|---|---:|---:|---:|
| mean | 107.8 | 124.6 | 16% |
| 범위 | 87.2 | 85.3 | 2% |
| 최대 샘플간 변화 | 57.5 | 53.8 | 7% |

**두 클래스의 진폭 특성이 사실상 같다.** 둘 다 "밝음 ↔ 어두움을 오간다"는 점이 동일하고,
다른 것은 **그 일이 얼마나 자주 일어나는가**뿐이다 (wave = 계속 흔듦, swipe = 간헐적).

이것이 뜻하는 바:

- **Spectral Analysis가 선택이 아니라 필수다.** 평균·분산·최대값 같은 요약통계만 쓰는
  블록으로는 두 클래스가 겹친다. 주파수 성분이 유일한 분리 근거다.
- 계획에 적었던 Raw + Flatten 베이스라인은 **이 두 클래스에서 실패할 것으로 예상된다.**
  실패하는 것을 확인하는 것 자체가 Spectral Analysis의 기여를 입증하는 대조군이 된다.
- 창 2000 ms(32 샘플)에 `swipe`가 몇 회 들어가는지는 **Phase 1의 긴 세션에서 실측한다.**
  (이 문서 초판에는 "1~1.5회"라고 적었는데, 그건 5초 측정에서 "3~4회 하세요"라고 지시한
  데서 나온 수치지 센서 특성이 아니다. 철회한다.)
  Phase 2 혼동행렬에서 둘이 섞이면 조치 순서는:
  1. 창을 3000 ms로 늘린다 (지연을 감수하고 주기 관측 횟수를 확보)
  2. 그래도 안 되면 `swipe`를 빼고 3-class로 축소한다 (계획의 조정 규칙)

Nyquist는 8 Hz라 손 흔들기(1~5 Hz)는 충분히 담긴다. 문제는 대역폭이 아니라
**창 안에 주기가 몇 번 들어가느냐**다.

## 5. 결론

- [x] 유효 샘플레이트 확보 → **HIGH / MTreg=31 / 16 Hz (센서 상한 19.0 Hz)**
- [x] 저해상도 모드 배제 (미완결 값 + 500배 잡음)
- [x] 밝은 환경 포화 없음 — 128 lx에서 raw 70/65535, 여유 충분
- [x] 드라이버 버그 2건 수정 및 실측 검증
- [x] 4개 클래스가 모두 idle 대비 분리되는가 → **3개 제스처 모두 분리 가능** (4절)
- [x] Phase 1 파라미터 확정: **HIGH / mt=31 / 62.5 ms 주기 / 창 2000 ms(32 샘플) / stride 500 ms**

**결론: 이 센서로 제스처 인식은 가능하다.** 배경 잡음이 1 LSB(1.9 lx)에 불과한 반면
제스처 신호는 50~90 lx 규모다. 신호 대 잡음 여유가 30배 이상이다.

### Phase 1(수집)로 넘길 것

- 샘플 주기 **62.5 ms (정확히 16 Hz)**, `edge-impulse-data-forwarder --frequency 16`
- `idle` 수집 시 **손·그림자가 센서 근처를 지나지 않도록** 특히 주의할 것.
  1차 측정에서 이미 한 번 당했다. 오염된 `idle`은 학습에서 조용히 성능을 갉아먹는다.

### Phase 2(학습)로 넘길 것

- **Spectral Analysis 필수** — `wave`와 `swipe`는 진폭 특성이 거의 같고(차이 2~7%)
  주파수 성분만이 유일한 분리 근거다 (4-1절).
- 둘이 혼동되면 창 2000 → 3000 ms, 그래도 안 되면 3-class로 축소.

### Phase 3(C 펌웨어)로 넘길 것

- fusion 디스크립터의 지원 주파수 목록에 **16.0 Hz**를 넣는다 (25 Hz도 16.6 Hz도 아님).
- C 드라이버를 직접 쓸 때 **MTreg lux 환산을 `raw / 1.2 * (69 / mt)`로 구현**한다.
  MicroPython 쪽과 스케일이 어긋나면 Phase 2 모델이 그대로 망가진다.
- L-Resolution 모드는 쓰지 않는다.
