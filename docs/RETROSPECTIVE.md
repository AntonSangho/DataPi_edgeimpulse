# 회고 — 1차 세션 (2026-08-05)

Phase 0부터 Phase 2 1차 학습까지 하루에 진행한 기록의 회고다.
**무엇을 만들었는가보다 어디서 시간을 잃었는가**를 남긴다.
이 프로젝트의 산출물이 절차서(`DATAPI_EI_GUIDE.md`)이므로, 이 문서도 그 재료다.

결과 요약: 검증 94.7% / 테스트 64.9%, `wave`가 테스트에서 붕괴(F1 0.07).
상세는 [`02-model.md`](02-model.md).

## 1. 가장 비쌌던 실수 — 얇은 근거로 만든 확신

`wave`와 `swipe`가 갈리는지를 **네 번 판단했고 답이 계속 뒤집혔다.**

| 시점 | 근거 | 판단 | 그 판단으로 한 일 |
|---|---|---|---|
| Phase 0 | 5초 측정, 진폭 차이 2~7% | 위험 | Spectral Analysis를 "필수"로 못박음 |
| 1차 수집 | 10초 세션, 눈으로 골 세기 | 넉넉히 갈림 | **페이스 메트로놈 기능 삭제** |
| 2차 수집 | 60초 세션 | 다시 위험 | 창 3000 ms 확대를 검토 |
| Feature explorer | 3D 투영 | 위험 | — |
| **1차 학습** | **혼동행렬** | **잘 갈림 (F1 0.97/0.98)** | — |

실제로는 **가장 잘 되는 부분**이었다. 그런데 그 사이에 이 추정을 근거로
기능을 넣고 뺐다. 메트로놈은 결과적으로 없애는 게 맞았지만,
**맞는 결정을 틀린 근거로 내렸다.**

### 무엇이 문제였나

셋 다 같은 오류다 — **표본이 작거나 차원이 낮은 관찰을 결론으로 승격시켰다.**

- 5초 / 10초 세션은 실사용 특성을 담지 못한다
- 그래프에서 눈으로 세는 골 개수는 ±50% 오차가 난다
- Feature explorer는 수십 개 특징 중 3개 축만 투영한다

### 다음에 할 것

**추정을 가설로 표시하고, 가설로는 코드를 바꾸지 않는다.**

> "10초 샘플에서 눈으로 세면 3.5~4배로 보인다. 60초 세션에서 확인 필요."

이렇게 썼다면 메트로놈 삭제를 그 시점에 하지 않았을 것이다.

## 2. 두 번째 실수 — 분모를 안 보고 백분율을 해석했다

검증 혼동행렬에서 `cover`가 11.1% `idle`로 갔다. 나는 이걸 두고:

- "`Take log of spectrum`이 절대 레벨 정보를 지웠다"는 **인과 이론**을 만들고
- 그걸 문서에 확정 서술로 적고
- 그 이론을 근거로 **Flatten 블록 추가**를 제안했다

백분율을 기약분수로 되돌려 보니:

```python
from fractions import Fraction
Fraction(0.111).limit_denominator(60)   # 1/9
```

| 클래스 | 검증 창 개수 | 오분류 창 |
|---|---:|---:|
| `cover` | **9** | **1** |
| `idle` | 20 | 1 |
| `swipe` | 30 | 1 |
| `wave` | 53 | 2 |

**창 하나였다.** 학습 세션이 클래스당 1개뿐이라 검증 세트가 한 자릿수였다.
이 규모에서는 창 하나가 두 자릿수 백분율을 만든다.

게다가 이론 자체도 틀렸다. [EI 공식 문서](https://docs.edgeimpulse.com/docs/edge-impulse-studio/processing-blocks/spectral-features)에
따르면 Spectral Analysis는 FFT bin과 함께 **RMS·skewness·kurtosis를 출력**한다.
필터가 `none`이므로 RMS에 DC가 그대로 들어간다 — `cover` ≈ 2, `idle` ≈ 145.
분리 특징이 이미 있었고, Flatten 추가는 **중복 제안**이었다.

### 다음에 할 것

- 백분율은 **분모를 확인하기 전까지 해석하지 않는다**
- 도구의 동작은 추측하지 말고 **문서를 읽는다** (`WebFetch` 한 번이면 됐다)
- 표본이 작으면 "원인 분석" 대신 **"표본이 작아 판단 보류"**라고 쓴다

## 3. 세 번 재녹화 — 조용히 실패하는 것들

같은 4개 클래스를 **세 번 다시 찍었다.** 매번 다른 이유였고, 매번 에러가 없었다.

| 회차 | 문제 | 왜 놓쳤나 |
|---|---|---|
| 1차 | 라벨 끝 공백 (`'idle '`), Sample length 10000 | 설정값만 알려주고 확인 방법을 안 줌 |
| 2차 | 축 이름에 라벨 목록 입력 (`idle coer wave swipe`) | 질문의 의미를 설명 안 함 |
| 3차 | `wave` 401/960 샘플로 잘림 | 샘플 수를 확인하라고 말 안 함 |

전부 **포워더 로그에 답이 찍혀 있었다.**

```
label: 'idle'                              ← 끝 공백
length: 60000                              ← 기본값 10000
sensor: 'Sensor with 1 axes (lux)'         ← 축 이름
Reading data from device OK (960 samples)  ← 잘림 여부
```

### 다음에 할 것

GUI/CLI 도구를 안내할 때는 **입력할 값**과 함께 **확인할 출력**을 준다.
사람이 값을 넣는 곳에는 반드시 검증 지점이 따라와야 한다.

이 4줄 체크리스트가 처음부터 있었다면 재녹화 2회(약 20분)를 아꼈다.

## 4. 잘 된 것 — 유지할 방식

### 부트스트랩을 먼저 돌렸다

16분 수집 계획 대신 **6분(train 4분 + test 2분)만 모아 학습**했다.
*AI at the Edge* Ch.9의 Bootstrapping이다. 결과로 세 가지를 알았고 **셋 다 예측과 반대**였다:

| | 예측 | 실제 |
|---|---|---|
| `wave`/`swipe` | 가장 위험 | 같은 조명에서 F1 0.97/0.98 |
| `cover`/`idle` | 분리 확실 | 검증에서 섞임 (표본 문제) |
| 진짜 병목 | 클래스 분리 가능성 | **일반화** |

16분을 다 모은 뒤였다면 문제는 발견해도 **어느 방향으로 고칠지** 몰랐을 것이다.

### test 세트를 다른 조명으로, 세션 단위로 분리했다

EI 자동 80/20 분할에 맡기지 않고 별도 세션(90 lux)으로 잡았다.
그 덕분에 검증 94.7% 뒤에 숨은 테스트 64.9%가 드러났다.
같은 세션을 나눴다면 90%대가 나왔을 것이고, Phase 3에서 실기로 확인했을 것이다.

### Model testing을 수정 작업보다 먼저 돌렸다

검증만 보고 Flatten 블록을 붙이려던 것을 테스트 결과가 막았다.
다만 이건 운에 가깝다 — 애초에 근거가 창 1개였다(2절).

### 하드웨어 실측을 계획보다 우선했다

Phase 0에서 계획의 가정(저해상도 139 Hz)이 틀렸고 드라이버 버그 2건이 나왔다.
데이터를 수백 개 모은 뒤였다면 전부 다시 모아야 했다.

## 6. 다음 세션에 적용할 것

1. **가설과 실측을 표기로 구분한다.** 가설로는 코드를 바꾸지 않는다.
2. **백분율은 분모부터 본다.** 세션이 늘기 전까지 혼동행렬 해석을 자제한다.
3. **수집 전 체크리스트 4줄**을 매번 확인한다 (3절).
4. **도구 동작은 문서로 확인**하고 말한다.
5. **포트 점유를 먼저 확인**하고, 검증이 필요하면 명시적으로 요청한다.
6. 세션을 하나 추가할 때마다 재학습해 **테스트 정확도 추이**를 본다.
   3세트를 몰아 찍고 한 번 학습하는 것보다 배우는 것이 많다.

## 8. 도구화 계획 — `datapi-ei-collect` 스킬

3절의 재녹화 3회와 포트 점유 왕복 3회는 **전부 기계가 확인할 수 있는 것**이었다.
현재 설치된 스킬 중 Edge Impulse/ML을 다루는 것은 없다
(`datapi-hwtest`가 가장 가깝지만 하드웨어 점검 전용이다).

별도 스킬로 만드는 편이 낫다고 본다 — `datapi-hwtest`는 "보드가 정상인가"를 묻고,
이쪽은 "수집 세션이 유효한가"를 묻는다. 성격이 다르다.

### 스킬이 할 일

| 단계 | 자동화 내용 |
|---|---|
| 사전 점검 | `fuser -v /dev/ttyACM0`로 포트 점유 확인, 점유 시 안내 후 중단 |
| 펌웨어 동기화 | `lib/` 및 `main.py` 최신화, `mpremote reset` |
| 스트림 검증 | 수 초 읽어 **실측 Hz**와 `SAMPLE_PERIOD_US` 일치 확인 |
| 체크리스트 출력 | 라벨/길이/축 이름/샘플 수 4줄을 녹화 전에 제시 |
| 로그 검증 | 포워더 로그를 파싱해 4개 항목 자동 판정 (PASS/FAIL) |
| 세션 기록 | `docs/01-data-collection.md`의 세션 표에 한 줄 추가 |

### 설계 메모

- `datapi-hwtest`의 구조를 참고한다 (`scripts/` + `lib/`, PASS/SKIP/FAIL 리포트).
- **로그 검증이 핵심 가치다.** 포워더를 스킬이 실행하지 않아도,
  사용자가 붙여넣은 로그를 파싱하는 것만으로 3절의 실수 3종을 전부 잡는다.
  이 부분만 먼저 만들어도 효용이 크다.
- 샘플 수 기댓값은 `길이(ms) / 62.5`로 계산한다. 하드코딩하지 않는다.
- 축 이름 기댓값(`lux`)과 클래스 목록은 스킬 인자로 받는다 —
  다른 센서로 확장할 때 재사용하기 위해서다.

### 만들 시점

**내일 수집을 한 번 더 해본 뒤**에 만든다. 세션 3세트를 찍으면서
어떤 확인이 실제로 반복되는지 보고, 그 다음에 `skill-creator`로 짠다.
지금 만들면 이번 세션의 실수만 방어하는 스킬이 될 위험이 있다.
