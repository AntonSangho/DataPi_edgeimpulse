# Phase 1 — 데이터 수집 (edge-impulse-data-forwarder)

> 상태: **부트스트랩 세트 수집 완료** — 조명 1세트(train) + 다른 조명 1세트(test)
> 나머지 조명 조건은 Phase 2의 혼동행렬을 보고 필요하면 추가한다

## 왜 data-forwarder인가

DataPi는 MicroPython 스택이고 Edge Impulse 공식 RP2040 펌웨어는 C 스택이다.
`edge-impulse-data-forwarder`는 시리얼로 들어오는 숫자 한 줄만 읽으므로,
**펌웨어를 빌드하지 않고** MicroPython 그대로 수집·학습까지 통과할 수 있다.

여기서 모은 데이터셋은 Phase 3의 C 펌웨어에서도 그대로 쓴다.

---

## 1. 설계 판단: 버튼으로 녹화를 제어하지 않는다

계획에는 "버튼(GP20)으로 녹화 시작, NeoPixel로 상태 표시"를 적었다.
**data-forwarder와 맞지 않아 폐기했다.**

포워더는 단방향이다. 장치는 계속 스트리밍하고, 어느 구간을 어떤 라벨로 저장할지는
Studio의 Data acquisition 탭이 정한다. 장치는 녹화 시작 시점을 알 방법이 없다.
버튼을 눌러 비프를 울려도 Studio의 녹화 구간과 정렬되지 않는다.

**대신 클래스마다 긴 연속 세션을 녹화한다.** 녹화 전체가 한 라벨이므로 시작 정렬이
아예 필요 없고, 창 분할은 EI가 알아서 한다. Phase 0의 5초 측정이 짧았던 문제도 함께 풀린다.

### 페이스 메트로놈을 넣었다가 뺐다

`wave`와 `swipe`가 빈도로만 갈릴까 봐(`docs/00` 4-1절) 버튼을 누르면 부저가
0.8/1.2/1.6초 간격으로 울려 속도를 잡아주는 기능을 넣었었다.
**1차 수집 실측 결과 불필요했고, 오히려 해로울 수 있어 들어냈다.**

자연스럽게 한 제스처가 이미 충분히 갈린다 (3절 실측 참고).
그리고 0.8초 박자에 맞춰 찍은 데이터로 학습하면 모델이 그 경직된 박자를 배우는데,
실사용에서 사람은 메트로놈 없이 제스처를 한다. 학습 데이터가 배포 조건과 어긋난다
(Ch.7 — representative dataset). 녹화 중 버튼 오조작으로 부저·LED가 켜져 세션을
오염시킬 위험도 있었다.

**제스처는 자연스럽게 한다.** 버튼·부저는 이 프로젝트에서 쓰지 않는다.

### NeoPixel 조도 오염 검증

GP21 NeoPixel이 BH1750 바로 옆에 있어 상태 표시등이 측정을 오염시킬 수 있다.
ON/OFF를 6회 교대해 주변광 드리프트를 상쇄시키고 측정했다.

| 색상 | OFF | ON | 차이 |
|---|---:|---:|---:|
| 흰색 255 | 124.02 | 125.38 | **+1.35 lux** |
| 녹색 64 | 125.34 | 124.97 | −0.37 lux |
| 적색 255 | 124.49 | 124.60 | +0.12 lux |

최댓값도 **1 LSB(1.86 lux) 미만**이다. `ei_forwarder.py`는 밝기 24 이하만 쓰므로
영향은 0.4 lux 이하 — 무시해도 된다.

(첫 시도에서는 밝기를 순차적으로 올리며 재봤는데 밝기와 무관하게 −3 lux가 나왔다.
15초 사이의 주변광 드리프트였다. 교대 측정으로 바꾸고서야 실제 값이 보였다.)

## 2. 실행

```bash
mpremote fs mkdir :lib
mpremote fs cp src/lib/bh1750.py :lib/bh1750.py
mpremote fs cp src/lib/bh1750_probe.py :lib/bh1750_probe.py
mpremote cp src/ei_forwarder.py :main.py   # 부팅 시 자동 실행
mpremote reset

edge-impulse-data-forwarder --frequency 16
```

첫 연결 시 축 이름을 물으면 **`lux`** 하나만 입력한다.

**EI 프로젝트**: `datapi light sensor` (ID `1079757`)

### 함정 6개

**(1) `--clean`은 프로젝트를 다시 묻지 않을 수 있다.**
계정에 프로젝트가 하나뿐이면 자동으로 그 프로젝트에 붙는다.
**Studio에서 새 프로젝트를 먼저 만들어야** 선택지가 나온다.

처음에 이걸 몰라서 기존 `Helloworld` 프로젝트에 붙었는데, 거기엔 8월 3일
**ADC 센서로 찍은 샘플이 남아 있었다.** 조도와 전혀 다른 신호가 같은 데이터셋에
섞이면 학습이 조용히 망가진다. 새 프로젝트를 만들어 옮겼다.

**(2) 포워더가 잡고 있으면 `mpremote`가 포트를 못 연다.**
스크립트를 고칠 때는 포워더를 먼저 종료할 것 (`fuser -v /dev/ttyACM0`로 확인 가능).

**(3) 라벨 끝의 공백을 EI는 다른 클래스로 취급한다.**
1차 수집에서 `'idle '`, `'cover '`, `'wave '`(공백 있음)와 `'swipe'`(없음)가 섞였다.
같은 동작이 두 클래스로 쪼개진다. Studio 라벨 입력란에서 **끝 공백을 반드시 확인**할 것.
포워더 로그의 `label:` 값에 그대로 찍히므로 거기서 확인할 수 있다.

**(4) Sample length 기본값은 10000 ms다.**
1차 수집에서 60000으로 바꾸는 걸 놓쳐 4개 클래스를 10초씩만 찍었다.
Label과 함께 **매번** 확인할 것.

**(5) 축 이름 질문에 라벨을 넣으면 안 된다.**
포워더가 `1 sensor axes detected. What do you want to call them?`이라고 묻는 것은
**축 이름**이다. 여기에 `idle coer wave swipe`를 넣어 축 하나의 이름이 그 문자열이 됐다.

Phase 3에서 막힌다. C 펌웨어의 fusion 디스크립터는 축을 `{"lux","lx"}`로 선언하는데,
EI는 학습된 모델이 기대하는 축 이름과 펌웨어가 제공하는 축 이름을 대조해 센서를 찾는다.
이름이 다르면 `AT+RUNIMPULSE`가 센서를 못 찾는다. **반드시 `lux`.**

로그의 `sensor: 'Sensor with 1 axes (lux)'`로 확인할 수 있다.

**(6) 샘플이 잘려도 포워더는 "OK"라고 말한다.**
1차 수집에서 60초를 요청했는데 `OK (401 samples at 16Hz)`가 찍혔다. 960이어야 한다.
장치 스트리밍이 도중에 멎은 것인데, 포워더는 받은 만큼 그대로 업로드한다.

**매 샘플마다 로그의 샘플 수를 확인할 것.**

| 요청 길이 | 기대 샘플 수 |
|---|---|
| 60000 ms | **960** |
| 30000 ms | **480** |

숫자가 다르면 그 샘플은 Studio에서 삭제하고 다시 찍는다.

## 3. 수집 계획

### 클래스

| 클래스 | 동작 | 주의 |
|---|---|---|
| `idle` | 무동작 | 손·그림자가 센서 위를 지나지 않게 |
| `cover` | 손으로 덮은 채 유지 | **녹화 전에 미리 손을 올려둘 것** |
| `wave` | 센서 위에서 좌우로 계속 흔들기 | 자연스럽게 |
| `swipe` | 손을 한 번씩 지나가게 | 자연스럽게 (박자 맞추지 말 것) |

### 1차 수집에서 실측된 신호 특성 (10초 세션, 배경 ~135 lx)

| 클래스 | 주파수 (60초 세션) | 골 깊이 |
|---|---:|---|
| `wave` | **~1.2 Hz** | 40~90 lux |
| `swipe` | **~0.6 Hz** | 10~30 lux |

**주파수는 약 2배, 골 깊이는 3배 이상 차이난다.**

> 10초 세션에서 눈으로 셌을 때는 1.9 Hz vs 0.5 Hz(3.5~4배)로 봤는데,
> 60초 세션에서 다시 세니 2배였다. 짧은 샘플에서의 눈대중은 과대평가였다.
> **주파수보다 진폭이 더 확실한 구분자다.** `docs/00` 4-1절에서 걱정한
"진폭으로는 구분 불가, 주파수만이 유일한 근거" 상황은 실제로는 오지 않았다.
Phase 0의 5초 측정에서는 두 동작을 비슷한 거리에서 했는데, 자연스럽게 하니
`wave`는 손을 가까이, `swipe`는 스쳐 지나가는 형태가 되어 진폭도 갈렸다.

→ 창 2000 ms 유지, 3-class 축소 불필요할 가능성이 높다. Phase 2에서 확정한다.

### Studio Collect data 설정

| 항목 | 값 |
|---|---|
| Label | `idle` / `cover` / `wave` / `swipe` (하나씩 바꿔가며) |
| Sample length (ms.) | **60000** (test는 30000) |
| Sensor | Sensor with 1 axes (lux) |
| Frequency | 16Hz |

기본값이 Label `adc` / length `10000`이므로 **매번 확인할 것.**

### 세션 구성

클래스당 조명 조건별로 1세션씩 녹화한다.

| | 조명 조건 | 세션 길이 | 클래스 | 합계 |
|---|---|---|---|---|
| train | 주광 / 형광등 / 스탠드 / 어두움 (4가지) | 60초 | 4 | 16분 |
| test | **별도 시간대·별도 조명** | 30초 | 4 | 2분 |

창 2000 ms / stride 500 ms 기준, 60초 세션 하나가 약 117개 창이 된다 (32 샘플/창).
train 16분이면 클래스당 약 470개 창 — 1축 소형 모델에는 충분하다.

### train/test는 반드시 세션 단위로 분리한다

**EI의 자동 분할(80/20)에 맡기지 말 것.** 같은 녹화 세션의 창이 train과 test 양쪽에
들어가면, 거의 동일한 신호를 외운 것이 테스트에서 맞는 것처럼 보여 성능이 크게
부풀려진다 (*AI at the Edge* Ch.7 — Splitting Your Data).

세션 단위로 나누면 "다른 시간, 다른 조명에서도 되는가"를 실제로 측정하게 된다.
Studio의 Data acquisition에서 test 세션은 업로드할 때부터 Testing 쪽으로 지정한다.

### `idle` 수집 시 주의

Phase 0에서 이미 한 번 당했다. `idle` 녹화 중 손이나 그림자가 센서 위를 지나가면
그 창은 사실상 `swipe`인데 `idle` 라벨이 붙는다. **라벨 노이즈**이고, 학습에서
조용히 성능을 갉아먹는다 (Ch.7 — Label Noise).

- 녹화 시작 후 센서에서 손을 완전히 치우고 그 자리를 벗어난다
- 사람이 지나다니는 통로 옆은 피한다
- 다만 **형광등 깜빡임, 창밖 구름, 조명 자동 조절**은 오히려 포함되어야 한다 —
  실사용에서 실제로 겪을 변화다

`idle`은 실사용 오검출을 좌우하는 클래스다. 다른 클래스보다 넉넉히 모아도 좋다.

## 6. 스트림이 멎는 문제 (수정됨)

1차 수집에서 `wave`가 401/960 샘플로 잘렸고, 이어서 `swipe`가 0 샘플로 두 번 실패했다
(`400 Bad Request`). 포워더를 재시작하니 정상으로 돌아왔다 —
포트 재연결이 DTR을 토글해 보드를 소프트 리셋시킨 것으로 보인다.

원인은 `sensor.measurement`의 I2C 예외로 추정한다. 예외가 루프를 빠져나가면
`main()`이 끝나고 REPL로 떨어져 출력이 완전히 멎는다. USB CDC 쪽 문제일 가능성도
있어 단정하지는 못한다.

**어느 쪽이든 스트림은 끊기지 않아야 한다.** `ei_forwarder.py`를 이렇게 고쳤다:

- 센서 읽기를 `try/except`로 감싸고, 실패하면 **직전 값을 내보내 주기를 유지**한다
- 연속 5회 실패하면 I2C와 센서를 통째로 다시 만든다 (NeoPixel이 흐린 빨강으로 바뀜)
- `main()`이 어떤 이유로든 빠져나오면 바깥 루프가 다시 시작한다
- 재초기화 시 `make_sensor(quiet=True)`를 쓴다 — I2C 스캔 결과를 찍으면
  그 줄이 데이터 스트림에 섞여 샘플로 읽힌다

직전 값을 반복해 내보내는 것은 데이터를 왜곡하지만, 스트림이 끊겨 세션 전체가
조용히 잘리는 것보다 낫다. 어차피 로그의 샘플 수로 이상을 잡아낼 수 있다.

## 7. 샘플레이트 정합성 — 반드시 지킬 것

장치 주기(62.5 ms)와 Studio 기록 간격(`--frequency 16` → 62.5 ms)이 **정확히 일치해야 한다.**

처음에는 장치가 60 ms(16.6 Hz)로 보내고 Studio는 62.5 ms로 기록해 4% 어긋나 있었다.
포워더 첫 연결 로그의 `interval: 62.5`를 보고 발견했다.

진폭 모델이면 무시할 수 있지만 **`wave`/`swipe`는 주파수로만 구분되므로 스펙트럼이
그대로 밀린다.** Phase 3에서 C 펌웨어가 16 Hz로 샘플링하면 학습 데이터와 또 어긋난다.

`--frequency` 값을 바꾸면 `bh1750_probe.py`의 `SAMPLE_PERIOD_US`도 함께 바꿀 것.

| `--frequency` | `SAMPLE_PERIOD_US` |
|---|---|
| 16 | 62500 |
| 12.5 | 80000 |
| 10 | 100000 |

센서 상한이 19 Hz이므로 16 Hz가 실질적인 최댓값이다.
