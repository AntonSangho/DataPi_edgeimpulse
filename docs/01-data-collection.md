# Phase 1 — 데이터 수집 (edge-impulse-data-forwarder)

> 상태: **수집 준비 완료** — 스크립트 검증 끝, 실제 녹화 대기

## 왜 data-forwarder인가

DataPi는 MicroPython 스택이고 Edge Impulse 공식 RP2040 펌웨어는 C 스택이다.
`edge-impulse-data-forwarder`는 시리얼로 들어오는 숫자 한 줄만 읽으므로,
**펌웨어를 빌드하지 않고** MicroPython 그대로 수집·학습까지 통과할 수 있다.

여기서 모은 데이터셋은 Phase 3의 C 펌웨어에서도 그대로 쓴다.

---

## 1. 설계 판단: 버튼으로 녹화를 제어하지 않는다

계획에는 "버튼(GP20)으로 녹화 시작, NeoPixel로 상태 표시"를 적었다.
**data-forwarder와 맞지 않아 폐기했다.**

포워더는 단방향이다. 장치는 계속 스트리밍하고, 어느 구간을 어떤 라벨로 저장할지는
Studio의 Data acquisition 탭이 정한다. 장치는 녹화 시작 시점을 알 방법이 없다.
버튼을 눌러 비프를 울려도 Studio의 녹화 구간과 정렬되지 않는다.

**대신 클래스마다 긴 연속 세션을 녹화한다.** 녹화 전체가 한 라벨이므로 시작 정렬이
아예 필요 없고, 창 분할은 EI가 알아서 한다. Phase 0의 5초 측정이 짧았던 문제도 함께 풀린다.

### 버튼의 실제 용도: 페이스 메트로놈

`wave`와 `swipe`는 진폭 특성이 거의 같고 **동작 빈도만 다르다** (`docs/00` 4-1절).
따라서 `swipe`를 일정한 속도로 반복하는 것이 분리의 열쇠다.

버튼을 누르면 부저가 일정 간격으로 울려 속도를 잡아준다. 스트리밍은 멈추지 않는다.

```
버튼(GP20) 누름 → OFF → 0.8초 → 1.2초 → 1.6초 → OFF ...
```

실측: 메트로놈이 켜져 있어도 샘플 간격은 59~61 ms, 목표(60 ms)에서 5 ms 이상
벗어난 샘플이 99개 중 **0개**다. 타이밍에 영향이 없다.

### NeoPixel 조도 오염 검증

GP21 NeoPixel이 BH1750 바로 옆에 있어 상태 표시등이 측정을 오염시킬 수 있다.
ON/OFF를 6회 교대해 주변광 드리프트를 상쇄시키고 측정했다.

| 색상 | OFF | ON | 차이 |
|---|---:|---:|---:|
| 흰색 255 | 124.02 | 125.38 | **+1.35 lux** |
| 녹색 64 | 125.34 | 124.97 | −0.37 lux |
| 적색 255 | 124.49 | 124.60 | +0.12 lux |

최댓값도 **1 LSB(1.86 lux) 미만**이다. `ei_forwarder.py`는 밝기 24 이하만 쓰므로
영향은 0.4 lux 이하 — 무시해도 된다.

(첫 시도에서는 밝기를 순차적으로 올리며 재봤는데 밝기와 무관하게 −3 lux가 나왔다.
15초 사이의 주변광 드리프트였다. 교대 측정으로 바꾸고서야 실제 값이 보였다.)

## 2. 실행

```bash
mpremote fs mkdir :lib
mpremote fs cp src/lib/bh1750.py :lib/bh1750.py
mpremote fs cp src/lib/bh1750_probe.py :lib/bh1750_probe.py
mpremote cp src/ei_forwarder.py :main.py   # 부팅 시 자동 실행
mpremote reset

edge-impulse-data-forwarder --frequency 16
```

첫 연결 시 축 이름을 물으면 **`lux`** 하나만 입력한다.
장치 이름은 `datapi-v03` 정도로 통일한다.

> 포워더가 잡고 있으면 `mpremote`가 포트를 못 연다. 스크립트를 고칠 때는
> 포워더를 먼저 종료할 것.

## 3. 수집 계획

### 클래스

| 클래스 | 동작 | 메트로놈 |
|---|---|---|
| `idle` | 무동작 | OFF |
| `cover` | 손으로 덮은 채 유지 | OFF |
| `wave` | 센서 위 10~20 cm에서 좌우로 계속 흔들기 | OFF (자연스럽게) |
| `swipe` | 비프에 맞춰 손을 한 번씩 지나가게 | **ON** |

### 세션 구성

Studio에서 **샘플 길이 60초**로 잡고 클래스당 조명 조건별로 1세션씩 녹화한다.

| | 조명 조건 | 세션 길이 | 클래스 | 합계 |
|---|---|---|---|---|
| train | 주광 / 형광등 / 스탠드 / 어두움 (4가지) | 60초 | 4 | 16분 |
| test | **별도 시간대·별도 조명** | 30초 | 4 | 2분 |

창 2000 ms / stride 500 ms 기준, 60초 세션 하나가 약 117개 창이 된다.
train 16분이면 클래스당 약 470개 창 — 1축 소형 모델에는 충분하다.

### train/test는 반드시 세션 단위로 분리한다

**EI의 자동 분할(80/20)에 맡기지 말 것.** 같은 녹화 세션의 창이 train과 test 양쪽에
들어가면, 거의 동일한 신호를 외운 것이 테스트에서 맞는 것처럼 보여 성능이 크게
부풀려진다 (*AI at the Edge* Ch.7 — Splitting Your Data).

세션 단위로 나누면 "다른 시간, 다른 조명에서도 되는가"를 실제로 측정하게 된다.
Studio의 Data acquisition에서 test 세션은 업로드할 때부터 Testing 쪽으로 지정한다.

### `idle` 수집 시 주의

Phase 0에서 이미 한 번 당했다. `idle` 녹화 중 손이나 그림자가 센서 위를 지나가면
그 창은 사실상 `swipe`인데 `idle` 라벨이 붙는다. **라벨 노이즈**이고, 학습에서
조용히 성능을 갉아먹는다 (Ch.7 — Label Noise).

- 녹화 시작 후 센서에서 손을 완전히 치우고 그 자리를 벗어난다
- 사람이 지나다니는 통로 옆은 피한다
- 다만 **형광등 깜빡임, 창밖 구름, 조명 자동 조절**은 오히려 포함되어야 한다 —
  실사용에서 실제로 겪을 변화다

`idle`은 실사용 오검출을 좌우하는 클래스다. 다른 클래스보다 넉넉히 모아도 좋다.

- [ ] **`swipe`의 실제 반복 주기가 몇 초인가** — 아래

### swipe 반복 주기 기록 (Phase 2 입력)

Phase 0에서 "창 2000 ms에 swipe가 1~1.5회밖에 안 들어간다"고 적었는데,
그 수치는 5초 측정 중 "3~4회 하세요"라는 **지시에서 나온 것이지 센서 특성이 아니다.**
실제 값은 여기서 정해진다.

메트로놈 간격을 기록하고, Studio에서 `swipe` 파형의 골(dip) 간격을 실측해 적을 것.

| 항목 | 값 |
|---|---|
| 사용한 메트로놈 간격 | (0.8 / 1.2 / 1.6초 중) |
| 실측 골 간격 | |
| 창 2000 ms 안의 반복 횟수 | |
| `wave`의 흔들기 주파수 | |

두 클래스의 반복 주파수가 2배 이상 떨어져 있으면 Spectral Analysis로 분리된다.
가까우면 창을 3000 ms로 늘리거나 3-class로 축소한다 (`docs/00` 4-1절).
